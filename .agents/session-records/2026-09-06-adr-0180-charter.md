## 2. Three premises corrected from the code, not from the prompt

The prompt named a channel expectation for each site's draw status and
told this session to *"correct each from the code"*. Three corrections
came back, and one of them narrows a ruling.

**(a) `select-person`'s carrier cannot be `fold/apply-events`, and
R-fold-carrier's LOCATION is therefore narrowed.** The site is called
from `prelude` (`run.clj:246`) — *"everything `run` computes before its
loop starts"* — where the whole `bindings` vector is built over the
arrival instants before one event has been folded. There is no
`apply-events` at that point to hang an index off. Fix-forward with
disclosure rather than a stop: one defensible reading, so
`rulings.md#R-stop-only-on-two-defensible-readings` does not bind. The
ruling's **law** (a maintained index whose from-scratch definition is
the gate) applies to all four sites unchanged; its **location** applies
to three, and `select-person`'s carrier is `prelude`'s own t-ascending
arrival sweep. Section *One disclosed narrowing of R-fold-carrier's
LOCATION* in the ADR is that disclosure.

**(b) `waiting-boarder` is draw-affecting through its RESULT, not its
own consumption** — the channel's expectation lands, for a different
reason than the one it gave. The function draws nothing and says so in
its own docstring (`decide.clj:971-976`), which is true. But a non-nil
answer takes a branch that draws twice: `bed-ready-transfer-event`
calls `bed-ready-location` with `world-rng` (`decide.clj:1143-1160`),
and `decide :bed-ready` additionally calls `vacate-bed` with
`facility-rng` (`decide.clj:1281-1283`). So the equivalence obligation
is identity of the RETURNED ID and of nil-vs-non-nil, not "a legal
boarder" — a strictly weaker claim an index can satisfy while moving
every byte after it. What makes that identity available at all is the
`[admitted-at patient-id]` sort key being a TOTAL order: the pid
tiebreak is why the answer does not depend on the `:patients` map's own
iteration order.

**(c) `occupancy-board` is not order-affecting, and the reason is
`free`.** The board reaches a draw only through `free`
(`facility.clj:56-84`), which uses it as a PREDICATE — `(remove board
ids)` over the derived, deterministically ordered `ids` list — so the
board's iteration order never reaches `choose`'s `(.nextInt rng (count
candidates))` (`facility.clj:113-118`). Only its KEY SET does. The
prompt's expectation was right; the reason is worth having in writing
because it is what tells a session which equality it owes. Two wrinkles
the ADR names rather than fixes, under `rulings.md#R-move-not-improve`:
`into {}` has a live hash-order dependence when two patients hold one
bed (`no-double-occupancy` forbids the state, so it is unreachable in a
clean log), and `decide.clj:1136` asks a SECOND query shape,
`(occupancy-board (dissoc (:patients world) patient-id))`. One site
reads the board's VALUES rather than its keys — `log_index.clj:182` —
so value equality is separately owed.

`last-uncancelled-index` came back as the prompt expected: neither draw-
nor allocation-affecting. The ADR states the argument anyway, and states
why "not draw-affecting" is not the same as "cheap to get wrong": a nil
where the scan returned an integer turns a legal cancel into a
`:step-rejected`, which is the mechanism that moved 21 `:cancel-transfer`
events in ADR-0179's own addendum.

## 4. The census predicate could not be satisfied, and the finding inverts

`scenario_census.clj`'s `:result-after-merge` counted a
`:result-available` whose own subject's status at the event was
`:merged`, and reported **zero on all eight cells**, which the
measurement record read as a structural gap: *"something in the ordering
makes the two mutually exclusive"*.

**ADR-0179's R-queue makes that predicate unsatisfiable rather than
rare.** A pending result FOLLOWS the survivor, so the subject a result
lands on is by construction the record that did not disappear. The
column was asking for a state the engine cannot produce, and it
correctly answered zero at every scale. The scenario the corpus
actually contains is R-inv's: a result whose **cited order names a
different subject**, joined to the result's own subject by a `:merge`
at `:t` at or before the result's `:t`.

Corrected and re-run over the same eight logs, still in `~/perf-out`:

| cell | after merge, before | after merge, corrected |
|---|---|---|
| `a2500-nopersons` | 0 | **15** |
| `a2500-persons` | 0 | **16** |
| `a7500-nopersons` | 0 | **20** |
| `a7500-persons` | 0 | **21** |
| `a7500-w3-persons` | 0 | **21** |
| `a7500-w9-persons` | 0 | **21** |
| `a22500-nopersons` | 0 | **30** |
| `a22500-persons` | 0 | **43** |

**The gate was 21 at 7,500 and it reads 21.** That is ADR-0179's own
addendum figure, derived there by a different route on the same
configuration — `derive-cells.sh`'s strongest check is that
`cell-a7500-persons.edn` is `demos/scenarios/dense-7500/config.edn`
byte for byte, and the run parameters match. Two instruments, one
answer.

**Two arithmetic claims were verified mechanically over both tables,
not asserted.** (i) The eight columns from `merges` rightward are
identical digit for digit on all eight cells, which is what says the
patch reached only the result arm. (ii) The merge column's population
came out of the two columns to its left, and the sum closes on every
cell: 14+1=15, 13+3=16, 16+4=20, 13+8=21 (×3), 25+5=30, 31+12=43.

`merges-forward` and `resolves-through-merges?` were re-derived from
ADR-0179's wording rather than called out of `check.clj` — they are
private there, and this namespace's own population-closure rule is that
an instrument sourced from the checker can only confirm the checker
agrees with itself. If the two ever disagree, that disagreement is the
finding.

**What this does NOT correct.** The zero-population claims in
`.agents/plans/2026-09-01-event-mutation-population-ledger.md` and in
ADR-0179 itself were counted over the 38 oracle roots and the
downstream fixture at 500 and 1,000, with the referential predicate,
and they are true there. This corrects one instrument over one set of
eight cells.

`measurements.md` got a **dated correction, not a rewrite**: the
original table and the original *"the merge column is zero"* section
stay verbatim, each with one anchor line marking it superseded, and the
corrected figures live in a new dated section beneath. The reasoning in
the withdrawn section is sound given its column; what was wrong was the
column.

## 6. Two gate-run disclosures

**The first background `make test` exited 127 without running anything,
and the log it appeared to have written was a STALE FILE from the
2026-09-05 session.** The harness path-translated `/tmp/runtest.sh` into
a Windows path, so the wrapper never executed; `/tmp/make-test-c2.log`
still held the previous session's 132,266-byte run, timestamped

gate that did not run. Caught by the timestamp. The wrapper moved to

and both runs were re-done clean. **Never read a gate log without
checking its mtime against the run you think produced it** — the
build-session rule about capturing `MAKE_EXIT` explicitly does not
protect against a log that predates the command.
