## Deviation record (dated, self-archived per this workspace's own convention)

Applied as given, no author present to ask (autonomous session, R30) — one methodology deviation and a couple of scope clarifications, no substantive rulings overridden:

**Step 1's first-attempt scan method was unreliable and had to be replaced.** `git grep -Il $'\r'` initially returned 27 files, not the ~13 the channel's own audit and this prompt's own context both expected. Root cause, confirmed by direct testing: passing a raw embedded CR byte as a `git grep` pattern argument through the `wsl -e bash -lc "..."` wrapper (Bash tool → `wsl.exe` → `bash -lc`) does not survive the crossing intact — `git grep $'\r'` matched essentially every line of several files that in fact contain no CR byte at all (verified directly with `git cat-file -p :<path> | grep -c $'\r'` returning 0 for one such file, `components/sim/src/ehrt/sim/check.clj`, while the `git grep` invocation had flagged it). This is the same family of hazard [[feedback-wsl-git-workflow]] already documents for heredocs and embedded newlines in commit messages through this same wrapper, now confirmed for a bare embedded control-byte pattern argument too. Fix: re-ran the scan as a byte-level pass over every tracked file's blob content (`git ls-files` + `git cat-file -p :<path>` + `grep -P '\r'`, i.e. the CR expressed as a Perl-regex escape sequence — plain ASCII text that survives the wrapper crossing intact, never a raw byte in the command-line argument itself). That pass found exactly 14 files: the 13 real CR-carrying text files (all already `-text`-covered by the existing `.gitattributes`, confirmed via `git check-attr`) plus one false positive, `logo.png`, whose CR byte is simply the fifth byte of the PNG file-signature magic number (`89 50 4E 47 0D 0A 1A 0A`) — already marked `binary` in `.gitattributes` and not a line-ending hazard of any kind. 13 real files matches the channel-cited count exactly. Recording this as a standing methodology note (a new feedback memory) rather than letting it be a one-off war story, since the same wrapper is used for every git operation in this environment.

**Step 3's "rows F4–F6" framing in the ruling was read as the area to check, not a claim that all three rows contained a bare citation.** Direct inspection found bare `F9`/`F14` citations only in F4 and F5 (the Index row for F5, plus the Register rows for F4 and F5); F6 (both Index and Register) cited nothing needing qualification.
