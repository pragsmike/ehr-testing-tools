This report extends the 2026-07-23 primary-source inventory (EXP-SBOM) with direct evidence gathering per the research protocol: NIST catalog/inventory checks, tool-page terms of use, authorship analysis, official distribution-channel discovery, and precedent search. All findings are dated 2026-07-23/24 and sourced from live queries against GitHub's API, NIST's public web properties, and the NIST-operated Maven repository discovered during this pass.

## Headline Finding: A Live, Official NIST Distribution Channel Exists

The single most consequential finding of this research phase is that **hit-nexus.nist.gov is a publicly reachable, unauthenticated, official NIST-operated Maven repository** that currently serves all six vendored coordinates the CDC wrapper depends on. Direct HTTP requests to `https://hit-nexus.nist.gov/repository/releases/` returned HTTP 200 for `gov.nist:hl7-v2-validation:1.7.3`, `gov.nist:hl7-v2-parser:1.7.3`, `gov.nist:hl7-v2-profile:1.7.3`, `gov.nist:xml-util:2.1.0`, `gov.nist.hit:hl7-v2-schemas:1.7.2`, and `com.github.hl7-tools:validation-report:1.2.0`, each resolving both `.pom` and `.jar` artifacts. This was previously assumed, based on the CDC wrapper's README, to be an internal or access-restricted system; it is not — it is open to the public internet, `robots.txt` only disallows crawler indexing of `/repository/` and `/service/`, not access. A byte-comparison of the published `hl7-v2-validation-1.7.3.jar` against the vendored copy in the CDC wrapper's `lib/` directory confirms they are identical artifacts with an identical, license-silent `META-INF/MANIFEST.MF` (vendor/version fields only, no license or copyright string in either copy).

This finding directly resolves Question E2. It means Adoption Mode 2 — fetch-at-build from an official source, rather than vendoring/redistributing jars inside a public Apache-2.0 repository — is cleanly available today for all six coordinates. Mode 2 requires only *use rights* (which the general NIST software disclaimer, Question B2 below, plausibly grants) and a *stable official source* (now confirmed to exist and be reachable). Mode 1 (public redistribution of vendored jars, including to users outside the US) still requires an explicit redistribution/foreign-copyright answer that the evidence below does not fully supply.

## Question-by-Question Findings

### A1 — NIST's official catalogs (code.nist.gov, code.gov)

`code.nist.gov` (a GitLab instance) was queried; its public "explore" listing does not surface `v2-validation`, `hl7-igamt`, or the six vendored coordinates by name, and no catalog record with a license field was found for any of the three subjects. `code.gov`'s federal source-code inventory API endpoint returned a redirect/404 during this session and no accessible current mirror of NIST's `code.json` was found; the file nominally hosted at `nist.gov/code.json` resolves to an HTML page rather than the machine-readable inventory, so no catalog-level license field could be retrieved for any of the three subjects. This is recorded as a negative finding, not evidence of non-listing — the inventory could exist behind an endpoint not resolved in this session.[^4]

### A2 — NIST-hosted tool sites, terms of use / disclaimers

Two distinct classes of statement were found. First, NIST's site-wide "Copyrights & Disclaimers" page carries a general software disclaimer applicable to "NIST-developed software," stating it may be used, copied, and distributed "AS IS" with attribution, and explicitly notes "software developed by NIST employees is not subject to copyright protection within the United States". Second, and more specific, a dedicated tool-portfolio page for the HL7 v2 conformance testing tools states directly: "NIST offers the tools and source code as public domain resources," in the context of the exact tool category — v2 message validation and profile-authoring tooling — that includes both `v2-validation` and `hl7-igamt`. This statement is a page-level assertion about "the tools" as a portfolio; it does not use the string "v2-validation" or "hl7-igamt," so it is classified Tier 4/borderline-Tier-2 (an official statement covering the tool category but not verbatim-naming the repositories). The IGAMT-2 and GVT legacy information sheets, current as of a 2026-05/06 transition to Prometheus Computing, describe hosting and account-migration terms but contain no license or copyright language.[^5][^3][^6][^2][^1]

### A3 — NIST Technical Series publications

No NIST Technical Series report (NISTIR, SP, etc.) describing `v2-validation` or `hl7-igamt` by name with an explicit software-availability/license statement was located. NIST conference materials and workshop slide decks describing the HL7 v2 tool family (e.g., a 2016 AIRA conference deck and a Snelick/Savage 2015 IGAMT-lite workshop deck) describe the tools functionally and list access URLs but do not include a licensing clause. One slide deck states the validation JAR/source code is "Free, in the public domain" as a bullet under "How to use the Validation Tool," which is directly on-point but appears only in presentation material rather than a controlling document.[^7][^8][^9]

### A4 — usnistgov org-wide license posture and sibling-repo comparison

The `usnistgov` GitHub organization maintains a template repository, `opensource-repo`, whose `LICENSE.md` contains the same standard "NIST Software Licensing Statement" quoted on `nist.gov/open/license` — establishing that NIST does have an org-level template that repos are meant to adopt. Sibling repos checked from the same technical group show inconsistent adoption: `usnistgov/grain-size-analysis-tools` and `usnistgov/trojai-example` (different NIST labs) both carry explicit `LICENSE.md`/`LICENSE.txt` files, demonstrating the template is used elsewhere at NIST. Within the Systems Interoperability / health-IT testing group specifically, `usnistgov/gvt-ui` (General Validation Tool UI, 4 contributors) was checked and shows no LICENSE file in its repository listing; `usnistgov/hl7-v2-validation-utils` and `usnistgov/hl7-v2-schemas` were also checked as siblings, with no LICENSE artifact surfaced in their public metadata. This indicates the absence of a LICENSE file in `v2-validation` and `hl7-igamt` is **consistent with group practice for this specific health-IT testing team**, not an isolated outlier — while other NIST labs (materials science, AI security) do apply the template. This is Tier-4 evidence: suggestive of team culture, not a license grant.[^10][^11][^12][^13][^14][^15]

### A5 — Repository history and Wayback checks

GitHub's commit-history API, queried with `path=LICENSE` against both `usnistgov/v2-validation` and `usnistgov/hl7-igamt`, returned zero commits for either repository — meaning no LICENSE file has ever existed at that path in the tracked git history of either repo. The Wayback Machine's availability API was queried for both repos' GitHub LICENSE blob URLs and returned no archived snapshots for either, which is inconclusive (Wayback rarely crawls that specific sub-path) rather than a confirmation of absence, but is consistent with the git-history finding. This distinguishes "never present" from "removed" for both subjects — the evidence supports never-present.

### B1/B2 — Authorship and the reach of 17 U.S.C. §105

Contributor-email analysis via the GitHub commits API shows all identifiable commit authors on `v2-validation` used `@nist.gov` addresses (`[redacted-contributor-address]`, `[redacted-contributor-address]`, `[redacted-contributor-address]`, `[redacted-contributor-address]`), and all identifiable commit authors on `hl7-igamt` likewise used `@nist.gov` addresses (`[redacted-contributor-address]`, `[redacted-contributor-address]`, `[redacted-contributor-address]`), with one contributor also appearing under a personal Gmail address (`[redacted-contributor-address]`) alongside their NIST address — consistent with the same individual committing from both a work and personal identity rather than an outside contributor. This is favorable evidence for §105 applicability (federal-employee authorship), but a critical caveat applies: GitHub commit author *email domain* is not proof of federal *employment status* — NIST's Systems Interoperability Group has historically used contractor staff (e.g., Prometheus Computing personnel are named as co-authors on NIST conference materials for this exact tool family), and contractor-authored code assigned to but not owned outright by NIST does not automatically inherit §105's public-domain status unless copyright was formally assigned. No commit in the sampled history was attributed to an `@prometheuscomputing.com` or other contractor domain, but the absence of contractor-domain commits in the *public* GitHub history does not rule out earlier or off-repository contractor authorship. This is reported as Reported/Inferred, not Verified, for both repos.[^16][^8]

On B2, NIST's canonical software-license statement (`nist.gov/open/license`, matching the `opensource-repo` template) explicitly addresses foreign copyright: it states NIST software "is generally not subject to copyright protection in the United States, but may be subject to foreign copyright (as per 17 U.S.C. §105)". Critically, unlike the parallel statement for NIST *data*, the software statement does **not** include the data statement's affirmative grant of "the non-exclusive irrevocable and unconditional right to print, publish, prepare derivative works and distribute the NIST data... on a royalty-free basis throughout the world" for any foreign copyright NIST might hold. The software statement is silent on what a worldwide redistributor may do about a foreign copyright — a materially different and weaker posture than the data statement's explicit worldwide grant. For a project distributing an Apache-2.0 repository worldwide, this gap is significant: the standard NIST software statement authorizes use/copy/distribution/modification "provided that you keep intact this entire notice," but does not affirmatively resolve whether that permission extends to jurisdictions where NIST could theoretically assert copyright.[^6]

### C1/C2 — Published copies and manifest evidence

Beyond the `hit-nexus.nist.gov` discovery above, `gov.cdc:lib-hl7v2-nist-validator` (the CDC wrapper itself) is separately published on Maven Central with a POM that explicitly declares Apache-2.0 licensing and lists `hit-nexus.nist.gov` as a `<repository>` source for its NIST dependencies — independently corroborating that this Nexus is the CDC team's own build-time dependency source, not merely an artifact of NIST's internal publish tooling. No `censes>` block appears anywhere in the officially served POMs for the six NIST-origin coordinates, and the officially served jar's manifest carries no license/copyright fields, matching the vendored copies byte-for-byte in that respect.[^17]

### D1/D2/D3 — Precedent search

A GitHub code/issue search for "license" scoped to `usnistgov/v2-validation` returned zero results; the same search scoped to `usnistgov/hl7-igamt` returned six results, all either dependency-bot version bumps or an unrelated UI configuration issue — none touching licensing substantively. A search scoped to `CDCgov/lib-hl7v2-nist-validator` for "license" returned zero issues or PRs. No adopter (state health department, vendor, HL7 community thread) publishing a license clarification, NOTICE attribution, or legal analysis specific to these three subjects was located in this pass. No FOIA reading-room or mailing-list record of a prior NIST response to an equivalent licensing inquiry was found. This absence is itself the finding: no precedent exists to shortcut the residual inquiry.[^18]

## Adoption-Mode Analysis (E2)

**Mode 1 — vendor/redistribute the jars inside the public Apache-2.0 repository.** This requires affirmative redistribution rights, including in jurisdictions outside the US where §105 does not apply. The evidence assembled satisfies the domestic half of this (the general NIST software statement permits copying and distribution "provided that you keep intact this entire notice," and commit-author evidence suggests NIST-employee authorship for both source repos, which is favorable to §105 applying at all). It does **not** satisfy the foreign-copyright half: the software statement is silent on worldwide redistribution rights in the way the parallel data statement is not, and no repository-specific or coordinate-specific declaration was found to close that gap.

**Mode 2 — fetch-at-build from an official source, sidestepping redistribution.** This requires only use rights and a stable official source. Both conditions are now substantially satisfied: `hit-nexus.nist.gov` is confirmed live, publicly reachable without authentication, and already used as the build-time source by the CDC wrapper's own Maven Central-published POM — this is about as "official" and "stable" a source as exists short of Maven Central itself. Use rights rest on the same general NIST software statement, which is unambiguous about *use*, *copy*, and *modification* domestically and does not carry the foreign-copyright ambiguity that specifically burdens *redistribution*. **Mode 2 is the adoption path least blocked by the evidence gathered.** It does not fully dissolve the problem — a truly loose end remains around whether "use" (fetching and compiling against the artifact at build time, without redistributing the jar itself) implicates foreign copyright at all — but that residual risk is materially smaller than Mode 1's.[^17]

## Residual Inquiry Recommendation (E3)

An inquiry to NIST is still warranted, but it can be narrowed considerably given the above. The two open questions that only NIST can answer are: first, whether the six named coordinates and the two named repositories are covered by the general software statement and the tool-portfolio's "public domain" language as a matter of NIST's own confirmation (closing the Tier-4-to-Tier-2 gap identified above); and second, whether NIST's position on foreign copyright for this specific software differs from the silence in the standard statement — i.e., whether NIST would object to, or affirmatively permit, redistribution of the vendored jars outside the United States. The most appropriate recipient is the NIST Systems Interoperability Group contact listed on the current HL7 v2 tool-portfolio and IGAMT/GVT transition pages, Robert Snelick (robert.snelick@nist.gov), who is named as the point of contact for this exact tool family as of the July 2026 transition notices; a secondary channel is NIST's general open-source program contact reachable via the `opensource-repo` template maintainers. Given the strength of the Mode 2 finding, the inquiry can be reframed from "please license this software" to a narrower confirmation request, which is both easier for NIST to answer and less likely to stall the project's go-public gate while awaiting a reply.[^3][^5]
