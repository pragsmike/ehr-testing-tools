# Component Selection Research for an Open-Source EHR Testing-Tools Repository

**Scope:** Synthetic longitudinal patient generation (HL7 v2 + FHIR, C-CDA later), controlled labelled mutation, structural + profile validation gates, and profile authoring/versioning — usable in-process or as a subprocess from Clojure/JVM, locally deployable, offline after one-time artifact acquisition, deterministic, free/OSS with transitive-license compatibility.

**Checked date:** 2026-07-22. Confidence markers used per keyed question: **Verified** (read the code/schema/test/issue that states it), **Reported** (stated by an authoritative primary doc but not code-verified), **Inferred** (deduced from cited evidence), **Unknown**. ⚠ marks load-bearing items requiring code/schema/test evidence or an explicit settling experiment. **Methods/limitations:** see final section.

---

## Executive Summary

**Strongest candidate per capability, with the single decisive fact (all dated to fetched sources):**

- **FHIR generation — Synthea** (Apache-2.0, MITRE): the only mature seeded JVM generator; native FHIR **R4/STU3/DSTU2**, C-CDA, CSV, CPCDS, **no R4B/R5, no HL7v2** ([Synthea README, fetched 2026-07-22](https://github.com/synthetichealth/synthea); [export source dir](https://api.github.com/repos/synthetichealth/synthea/contents/src/main/java/org/mitre/synthea/export)). Latest tagged release **v4.0.0, published 2026-03-05** ([Synthea releases API](https://api.github.com/repos/synthetichealth/synthea/releases?per_page=2)).
- **HL7 v2 generation — none adopt-ready**: Synthea has no mainline v2 exporter; the only v2 code is an unmerged 2021 PR its own author calls "a bit of a hack… not suitable for inclusion" ([PR #862](https://github.com/synthetichealth/synthea/pull/862)). Recommended path: a purpose-built `PatientExporter` plugin ([Custom Exporters wiki](https://github.com/synthetichealth/synthea/wiki/Custom-Exporters)) projecting to v2 via **HAPI HL7v2** ([Maven Central `ca.uhn.hapi:hapi-base`](https://search.maven.org/solrsearch/select?q=g:ca.uhn.hapi+AND+a:hapi-base&rows=3&wt=json)).
- **FHIR validation — official validator `org.hl7.fhir.core` / `validator_cli`** (Apache-2.0, HL7-maintained), latest **6.9.12 published 2026-07-15** ([release 6.9.12](https://github.com/hapifhir/org.hl7.fhir.core/releases/tag/6.9.12)). HAPI FHIR's validator is the **same engine** wrapped differently ([HAPI instance validator docs](https://hapifhir.io/hapi-fhir/docs/validation/instance_validator.html)).
- **HL7 v2 profile validation — CDC `lib-hl7v2-nist-validator`** (Apache-2.0) wrapping the **NIST `v2-validation`** Scala engine, which is the only surveyed engine that enforces predicates/co-constraints, verified in engine source ([NIST content `DefaultValidator.scala`](https://raw.githubusercontent.com/usnistgov/v2-validation/master/validation/src/main/scala/hl7/v2/validation/content/DefaultValidator.scala)). HAPI HL7v2's in-process `DefaultValidator` enforces usage/cardinality/length/table only ([HAPI `DefaultValidator.java`](https://raw.githubusercontent.com/hapifhir/hapi-hl7v2/master/hapi-base/src/main/java/ca/uhn/hl7v2/conf/check/DefaultValidator.java)).
- **Profile authoring — FSH + SUSHI** (Apache-2.0, Node.js 18, not JVM) for FHIR ([SUSHI README](https://github.com/FHIR/sushi)); **IGAMT** (Spring Boot + MongoDB + Angular) for HL7 v2 conformance profiles ([hl7-igamt pom.xml](https://raw.githubusercontent.com/usnistgov/hl7-igamt/master/pom.xml)).
- **Mutation — none adopt-ready** in surveyed repositories; build in-house (see B1 for scope of search).

**Three findings that most shape the design:** (1) the official FHIR validator is **not cleanly offline** — even with locally packaged ValueSets, `-tx n/a` produces different, failing results, an **open** bug with no fix as of 2026-07-22 ([issue #2272, state open](https://github.com/hapifhir/org.hl7.fhir.core/issues/2272)); (2) it has a **live, non-deterministic concurrency bug** in `ProfileUtilities.fixTypeOfResourceId()`, **open**, unpatched through 6.9.9 ([issue #2470, state open](https://github.com/hapifhir/org.hl7.fhir.core/issues/2470)); (3) the IGAMT export bundle and HAPI's `message_profile.xsd` are **different profile dialects** ([HAPI `ProfileParser.java`](https://raw.githubusercontent.com/hapifhir/hapi-hl7v2/master/hapi-base/src/main/java/ca/uhn/hl7v2/conf/parser/ProfileParser.java); [CDC lib README](https://github.com/CDCgov/lib-hl7v2-nist-validator)), so IGAMT profiles route to the NIST/CDC engine, not HAPI.

**License spine:** Apache-2.0 for Synthea, official validator, HAPI FHIR, SUSHI, Inferno, CDC wrapper. **HAPI HL7v2 is dual MPL/GPL with a user *choice* of either license — GPL is not mandatory** ([HAPI HL7v2 pom.xml license block](https://raw.githubusercontent.com/hapifhir/hapi-hl7v2/master/pom.xml)). NIST `v2-validation` and IGAMT ship **no LICENSE file** (resolved below as far as primary sources allow). Terminologies split sharply: LOINC and UCUM are royalty-free-redistributable with notice; **SNOMED CT and CPT require licenses**; ICD-10-CM is distributed free by CMS/CDC.

**Questions resolvable only by experiment (defined in Proposed Experiments):** Synthea byte/order determinism across thread counts (A4); HAPI FHIR parser round-trip fidelity (B2); OperationOutcome code/location stability across pinned versions (C3); minimal freely-redistributable offline terminology set (C5); IGAMT-`PROFILE.xml`-vs-HAPI-XSD compatibility (D1); CDC-lib fully-offline build (D3); and startup/memory/throughput for every candidate (E6). *No final architecture is recommended; options are ranked with tradeoffs and kept separable from findings.*

## Findings by Question

### A. Synthetic Generation

#### A1 — Generators, native formats and versions (survey scope stated)
**Answer:** Synthea is the only mature seeded longitudinal JVM generator. Native outputs: **HL7 FHIR R4, STU3 (3.0.1), DSTU2 (1.0.2); Bulk FHIR ndjson; C-CDA; CSV; CPCDS** — **no FHIR R4B/R5 and no HL7v2**. **Search scope for alternatives:** GitHub repository/topic search and org-scoped queries for FHIR/HL7v2 generators and converters (`synthetichealth`, `LinuxForHealth`, `microsoft`, `nextgenhealthcare`, `usnistgov`), plus general web search on synthetic-patient and FHIR-tooling indexes. Surfaced alternatives and their constraints: **`FHIRTestResourceGenerator`** (Java, single-resource randomizer, not longitudinal, license NOASSERTION); **Inferno reference generators** (Ruby, non-JVM); **Crucible** (archived); hosted/proprietary EHR sandboxes (not local). No maintained JVM generator with native HL7v2 output was found within this scope.
**Evidence:** format table in [Synthea README](https://github.com/synthetichealth/synthea); exporter classes (`FhirR4/FhirStu3/FhirDstu2`, `CCDAExporter`, `CPCDSExporter`, `CSVExporter`, no v2 file) in [export source dir](https://api.github.com/repos/synthetichealth/synthea/contents/src/main/java/org/mitre/synthea/export); [FHIRTestResourceGenerator](https://github.com/geloro94/FHIRTestResourceGenerator) (Java, single-resource); [Crucible archived listing](https://ecqi.healthit.gov/tool/crucible).
**Version/date:** Synthea README + release v4.0.0 (2026-03-05); fetched 2026-07-22.
**Confidence:** Formats/versions **Verified**; universal-absence claim bounded to the stated search scope → **Inferred**.

#### A2 ⚠ — Synthea HL7v2 exporter (versions/types/segments/quality/maintenance)
**Answer:** **No HL7v2 exporter exists in mainline Synthea.** The only v2 code is unmerged **PR #862** (2021): `HL7V2Exporter.java` (~626 lines) emitting "fat" **ADT** messages via **HAPI HL7v2 2.5.1**, with `MSH/PID/PD1/IN1/SFT` plus meds/labs/vitals and custom Z-segments, gated on `exporter.hl7v2.export`. **Closed by its own author** as "too use-case specific… a bit of a kludge… not suitable for inclusion." Feature request **#1561 (opened 2025-02-12) is open with no maintainer commitment**. The endorsed forward path is a `PatientExporter` ServiceLoader plugin.
**Evidence (PR/issue/code, per ⚠):** [PR #862, state Closed](https://github.com/synthetichealth/synthea/pull/862) — adds `HL7V2Exporter.java (626)`, "Change HAPI to 2.5.1", "Added a minimal IN1, SFT and PD1 segment"; author (2024-08-03) "was a bit of a hack and not suitable for inclusion"; maintainer cites `PatientExporter.export(Person, long, ExporterRuntimeOptions)`. [Issue #1561, state open](https://github.com/synthetichealth/synthea/issues/1561).
**Confidence:** **Verified.**

#### A3 — FHIR→v2 converters, standalone v2 generators, template methods, minimal projection (expanded)
**Answer:** Direct FHIR→HL7v2 conversion tooling is scarce and constrained:
- **Microsoft `FHIR-Converter`** (MIT): supports **FHIR→HL7v2 (Preview)** plus HL7v2/C-CDA→FHIR, via **Liquid templates on the .NET runtime — not JVM** ([FHIR-Converter README](https://raw.githubusercontent.com/microsoft/FHIR-Converter/main/README.md); [repo/license MIT](https://github.com/microsoft/FHIR-Converter)). Active (pushed 2026-06-03).
- **Mirth Connect / NextGen `connect`** (**MPL 2.0**, single copyleft, **Java**): channel + template (JavaScript/velocity) transformation engine that can map FHIR↔HL7v2; general-purpose integration engine, not a purpose-built projector ([Mirth LICENSE = Mozilla Public License 2.0](https://github.com/nextgenhealthcare/connect/blob/master/LICENSE)). Last push 2024-09-23 ([repo metadata](https://api.github.com/repos/nextgenhealthcare/connect)).
- **LinuxForHealth `hl7v2-fhir-converter`** (active, pushed 2026-02-11) converts **v2→FHIR only** (wrong direction) ([LinuxForHealth repository](https://github.com/LinuxForHealth/hl7v2-fhir-converter)).
- **Caristix / HL7-Soup / Message Workbench:** commercial or Windows-desktop tooling; not evaluated as OSS/JVM libraries within scope (no maintained OSS JVM library surfaced).
Building blocks for a JVM projection: **HAPI HL7v2** typed structures/encoders (Maven Central) and **Synthea's in-repo `flexporter`** FHIRPath mapping engine. **Minimal purpose-built projection estimate:** a Synthea `PatientExporter` plugin emitting ADT^A01/A04 (`MSH/EVN/PID/PV1`, optionally `AL1/DG1/PR1/OBX/IN1`) — small-to-medium effort by analogy to the 626-line 2021 PR.
**Evidence:** direction/runtime facts cited above; `flexporter` files (`Actions.java`, `CustomFHIRPathResourceGeneratorR4.java`, `Mapping.java`) in [flexporter source dir](https://api.github.com/repos/synthetichealth/synthea/contents/src/main/java/org/mitre/synthea/export/flexporter); plugin interface in [Custom Exporters wiki](https://github.com/synthetichealth/synthea/wiki/Custom-Exporters).
**Confidence:** Converter capabilities/licenses/directions **Verified**; effort estimate **Inferred**.

#### A4 ⚠ — Byte determinism; complete pinned-input list; nondeterminism evidence
**Answer:** Populations are **reproducible per (seed + Synthea version + config)**; thread count does **not** change *which* patients are produced because each person's seed is drawn sequentially from the population RNG before thread submission. **Byte-determinism additionally requires pinning:** `-s` (population seed), `-cs` (clinician seed), `-r` (reference date) — all default to `System.currentTimeMillis()` — plus the Synthea **version**, module set (`-d`), config (`-c`), locale/geography, and `generate.thread_pool_size` (defaults to `availableProcessors()`). Output-file *ordering* across differing thread counts is **Unknown** (experiment EXP-A4).
**Evidence (code, per ⚠):** `seed = referenceTime`, `clinicianSeed = referenceTime`, `referenceTime = System.currentTimeMillis()`; `threadPoolSize = Config.getAsInteger("generate.thread_pool_size", -1)` → `availableProcessors()`; per-person seed `final long seed = this.populationRandom.randLong(); threadPool.submit(() -> generatePerson(index, seed));` in [Generator.java](https://raw.githubusercontent.com/synthetichealth/synthea/master/src/main/java/org/mitre/synthea/engine/Generator.java). Vendor identity claim "populations generated with the same seed and the same version of Synthea should be identical" in [Basic Setup wiki](https://github.com/synthetichealth/synthea/wiki/Basic-Setup-and-Running).
**Confidence:** Seed/thread independence and required pins **Verified**; exact byte-identical file ordering across thread counts **Unknown** (EXP-A4).

#### A5 — Network fetches / offline disablement
**Answer:** Synthea runs fully locally from the fat JAR; geography/module data ship in resources, and the US Core IG flag selects bundled profiles rather than downloading. No mandatory runtime network fetch was found in the run path read.
**Evidence:** local-only `java -jar` invocations in [Basic Setup wiki](https://github.com/synthetichealth/synthea/wiki/Basic-Setup-and-Running); bundled MA/US data in [Common Configuration wiki](https://github.com/synthetichealth/synthea/wiki/Common-Configuration); only console prints (no network) in the read section of [Generator.java](https://raw.githubusercontent.com/synthetichealth/synthea/master/src/main/java/org/mitre/synthea/engine/Generator.java).
**Confidence:** **Inferred** (not exhaustively audited across every exporter).

#### A6 — JVM library/subprocess (functional integration only; resource profile in E6)
**Answer:** Usable in-process (`Generator`) or as a subprocess (`java -jar synthea-with-dependencies.jar …`); requires **JDK 11+ (LTS 11/17 recommended)**; multi-threaded fixed pool sized to CPU count. Concrete startup/memory/throughput → see **E6** (Unknown; benchmark EXP-E6).
**Evidence:** JDK requirement in [Synthea README](https://github.com/synthetichealth/synthea); threading in [Generator.java](https://raw.githubusercontent.com/synthetichealth/synthea/master/src/main/java/org/mitre/synthea/engine/Generator.java).
**Confidence:** JVM/subprocess/Java version **Verified**; performance **Unknown** (E6).

#### A7 — Custom modules/exporters and learning curve
**Answer:** Two seams: JSON disease/care modules and custom exporters (`PatientExporter` per-patient, `PostCompletionExporter` once) loaded as drop-in JARs via Java **ServiceLoader** (`META-INF/services/…`), documented as "fairly simple," requiring JVM code (Kotlin/Scala possible).
**Evidence:** interfaces, `./gradlew jar`, `-cp`/`./lib/custom/`, example project in [Custom Exporters wiki](https://github.com/synthetichealth/synthea/wiki/Custom-Exporters).
**Confidence:** **Verified.**

#### A8 — Directly controllable characteristics vs filtering/seed-search
**Answer:** Direct controls: population size (`-p`), gender (`-g`), age range (`-a`), geography. Finer targeting is **filter/retry-based** (`checkCriteria` + `maxAttemptsToKeepPatient` re-roll loop), i.e., seed-search, not direct synthesis.
**Evidence:** flags in [Basic Setup wiki](https://github.com/synthetichealth/synthea/wiki/Basic-Setup-and-Running); retry loop `do{…createPerson…checkCriteria…}while(!patientMeetsCriteria)` in [Generator.java](https://raw.githubusercontent.com/synthetichealth/synthea/master/src/main/java/org/mitre/synthea/engine/Generator.java).
**Confidence:** **Verified.**

### B. Mutation

#### B1 — Open-source controlled/labelled mutators (search scope stated)
**Answer:** **No maintained open-source mutator emitting FHIR/HL7v2 defects labelled with (operator, location, violated constraint) was found in the surveyed repositories/indexes.** **Search scope:** GitHub repository/topic/code search for "FHIR mutation", "HL7 fuzzer", "structure-aware fuzzing", healthcare test-data mutation; general web search across FHIR-tooling indexes and HL7 security materials. Found: **`IOActive/HL7-Fuzzer`** (MIT, **Python**, security-oriented, unlabelled, last push 2021-01-13, [GitHub repository metadata](https://api.github.com/repos/IOActive/HL7-Fuzzer)); generic mutators **Radamsa** and libFuzzer/`Arbitrary` (cited in [HL7 "Fuzzing with FHIR" materials](https://info.hl7.org/hubfs/FHIR%20Open%20Source%20Tooling%20Webinar%20Series/PDFs/FHIR%20Security%20Education%20Event%20-%20Fuzzing%20with%20FHIR%20-%20FINAL%20Brett%20P%20Stringham-V3.1%20Brett%20Stringham.pdf)); and **`FHIRTestResourceGenerator`** (Java, controlled FHIRPath-map modification, no defect taxonomy, [FHIRTestResourceGenerator repository](https://github.com/geloro94/FHIRTestResourceGenerator)).
**Confidence:** Verified-absence **bounded to the stated scope** → **Inferred** for the universal claim.

#### B2 ⚠ — Round-trip fidelity (HAPI HL7v2 code-verified; HAPI FHIR by experiment)
**Answer:** **HAPI HL7v2 `PipeParser` round-trip is canonicalizing, not byte-exact:** on encode it **strips trailing/extra delimiters** at field and segment level, dropping trailing empty fields; a `forceUpToFieldNum` option can re-pad to a minimum field count. Mutation harnesses must therefore mutate the encoded string or verify post-encode. **HAPI FHIR JSON/XML parser fidelity is Unknown** (not code-verified) → EXP-B2.
**Evidence (code, per ⚠):** `stripExtraDelimiters(...)` "search from back end for first occurrence of non-delimiter" and "strip trailing delimiters …" with `forceUpToFieldNum` re-padding in [PipeParser.java](https://raw.githubusercontent.com/hapifhir/hapi-hl7v2/master/hapi-base/src/main/java/ca/uhn/hl7v2/parser/PipeParser.java). HAPI FHIR parsers "very lightweight … do not need to be reused" in [HAPI intro docs](https://hapifhir.io/hapi-fhir/docs/getting_started/introduction.html).
**Confidence:** HL7v2 canonicalization **Verified**; HAPI FHIR byte-fidelity **Unknown** (EXP-B2).

#### B3 — Healthcare defect taxonomies; generic vs format-specific (broadened)
**Answer:** No canonical healthcare *mutation* taxonomy found; the operative error taxonomies to mutate against are: FHIR **OperationOutcome issue codes** (`code-invalid`, `structure`, `invalid`, `required`, …); HL7 v2 HAPI exception classes (`ProfileNotFollowedException`, `ProfileNotHL7CompliantException`, `XElementPresentException`) and NIST report classifications (**ERROR/WARNING/ALERT/AFFIRMATION**); C-CDA schema + Schematron rule IDs. Broader mutation-testing prior art (generic, not healthcare-specific) includes property-based generators and mutation-testing frameworks (e.g., PIT/mutation operators), which supply operator vocabularies (replace/insert/delete/boundary) reusable as mutation-operator labels.
**Evidence:** FHIR codes/expressions in [issue #2272](https://github.com/hapifhir/org.hl7.fhir.core/issues/2272); HAPI v2 exception types in [conf/check dir](https://api.github.com/repos/hapifhir/hapi-hl7v2/contents/hapi-base/src/main/java/ca/uhn/hl7v2/conf/check); NIST classifications ERROR/WARNING/ALERT/AFFIRMATION in [CDC lib README](https://github.com/CDCgov/lib-hl7v2-nist-validator); C-CDA schema+Schematron in [C-CDA companion guide](https://build.fhir.org/ig/HL7/CDA-ccda-2.1-sd/understanding_c-cda_and_the_c-cda_companion_guide.html).
**Confidence:** Operative error taxonomies **Verified**; dedicated mutation taxonomy **Verified absence** (scoped).

#### B4 — Mutation-provenance schemas/conventions (broadened)
**Answer:** No healthcare-specific mutation-provenance schema found. Reusable location grammars for an (operator, location, violated-constraint) label: **FHIRPath** expressions (used by the validator's OperationOutcome `expression` and by `FHIRTestResourceGenerator`'s FHIRPath→value map) for FHIR; **HL7 v2 Terser paths** (`GROUP/SEGMENT-field(rep)-component-subcomponent`) for v2. Generic provenance conventions from mutation testing (mutant ID + operator + target location + kill status) map cleanly onto these.
**Evidence:** OperationOutcome `expression` FHIRPath locations in [issue #2272](https://github.com/hapifhir/org.hl7.fhir.core/issues/2272); FHIRPath-map approach in [FHIRTestResourceGenerator](https://github.com/geloro94/FHIRTestResourceGenerator); Terser paths (`currentTerserPath`) in [PipeParser.java](https://raw.githubusercontent.com/hapifhir/hapi-hl7v2/master/hapi-base/src/main/java/ca/uhn/hl7v2/parser/PipeParser.java).
**Confidence:** **Inferred** (no dedicated schema; natural conventions identified).

### C. FHIR Validation

#### C1 ⚠ — Exact current offline procedure, cache locations, air-gapped invocation, cache bugs
**Answer:** Two **distinct caches** are involved:
- **Package cache** (FHIR IG NPM tarballs). Default locations, verified from `FilesystemPackageCacheManager` source: user cache `${user.home}/.fhir/packages`; system cache Windows `${ProgramData}/.fhir/packages`, else `/var/lib/.fhir/packages`; temp `[tmp]/.fhir/packages`; overridable via a builder `withCacheFolder(path)`. Default package servers are `packages.fhir.org`/`packages2.fhir.org`, and **default servers can be disabled** via `FhirSettings.isIgnoreDefaultPackageServers()` (the air-gap knob), with network access routed through `ManagedWebAccess`.
- **Terminology cache** (tx server responses), a separate location surfaced in the log and set by `-txcache <dir>`, cleared with `-clear-tx-cache`, or disabled with `-txcache n/a`.

**One-time acquisition (online):** fetch `validator_cli.jar` from GitHub releases (6.9.12) or Maven `ca.uhn.hapi.fhir:org.hl7.fhir.validation.cli`; pre-load each IG and its transitive dependencies (pinned `id#version`) into `${user.home}/.fhir/packages`; optionally warm the terminology cache.
**Fully air-gapped invocation:** disable default package servers (FhirSettings), then `java -jar validator_cli.jar -version 4.0.1 -ig hl7.fhir.us.core#<ver> -tx n/a -txcache <local-dir> src.json` reading only local caches.
**Known offline/version-skew/cache bugs (status as of 2026-07-22):** (a) **#2272** — `-tx n/a` still fails ValueSet-membership/slice/display checks even for package-local ValueSets: **open, no fixed version found**; (b) **#2524** — `TerminologyCache` persists transient tx failures, poisoning the on-disk cache: **open, no fixed version found**; (c) **#2462** — locale-sensitive behavior can break local builds on non-English JVM locales: **open, no fixed version found**; (d) a proxy-for-HTTPS CLI issue was **closed** (unrelated to air-gap). No issue establishing a fixed version for the offline-terminology coupling was found.
**Evidence (per ⚠):** cache paths `${user.home}/.fhir/packages`, `${ProgramData}/.fhir/packages`, `/var/lib/.fhir/packages`, `[tmp]/.fhir/packages`, `withCacheFolder`, `isIgnoreDefaultPackageServers`, `ManagedWebAccess` in [FilesystemPackageCacheManager.java](https://raw.githubusercontent.com/hapifhir/org.hl7.fhir.core/master/org.hl7.fhir.utilities/src/main/java/org/hl7/fhir/utilities/npm/FilesystemPackageCacheManager.java); `-tx n/a`, `-txcache`, `-clear-tx-cache`, `-ig id#version` in [Using the FHIR Validator (HL7 confluence)](https://confluence.hl7.org/spaces/FHIR/pages/35718580/Using+the+FHIR+Validator); tarball registry + pinned versions in [FHIR packages spec](https://hl7.org/fhir/packages.html); [release 6.9.12 (2026-07-15)](https://github.com/hapifhir/org.hl7.fhir.core/releases/tag/6.9.12); bug states [#2272 open](https://github.com/hapifhir/org.hl7.fhir.core/issues/2272), [#2524 open](https://github.com/hapifhir/org.hl7.fhir.core/issues/2524), [#2462 open](https://github.com/hapifhir/org.hl7.fhir.core/issues/2462).
**Confidence:** Cache paths/flags/air-gap knob **Verified**; residual offline failures **Verified** (open bugs); minimal terminology that yields a clean offline pass **Unknown** (EXP-C5).

#### C2 — Library vs subprocess; Java, global state, API stability (resource profile in E6)
**Answer:** Both entry points exist. **Subprocess** isolates global state/version — recommended for determinism/CI. **Library** (Maven `org.hl7.fhir.validation.cli`) avoids process spawn but exposes shared mutable caches (see #2470) and requires wiring package/terminology support in code. **Java 11+ (JDK 11/17 tested).** Validation-support interfaces were reworked in HAPI 5.x (`IContextValidationSupport`→`IValidationSupport`). Memory/startup → **E6**.
**Evidence:** library/CLI + Maven coords + Java 11 min in [org.hl7.fhir.core README](https://github.com/hapifhir/org.hl7.fhir.core); JDK 11/17 tested in [confluence](https://confluence.hl7.org/spaces/FHIR/pages/35718580/Using+the+FHIR+Validator); concurrency/global-state hazard in [issue #2470](https://github.com/hapifhir/org.hl7.fhir.core/issues/2470); API rework in [HAPI instance validator docs](https://hapifhir.io/hapi-fhir/docs/validation/instance_validator.html).
**Confidence:** **Verified.**

#### C3 ⚠ — OperationOutcome stability across versions
**Answer:** Message **text is not stable** across releases (release notes routinely reword messages), and terminology configuration changes both which issues appear and their `code`. `expression`/`code` are more stable than `details.text` but not guaranteed. **CI gates should assert on `{severity, code, expression}` with pinned validator+IG+terminology.** A full code/location stability matrix requires diffing two pinned versions → EXP-C3.
**Evidence (per ⚠):** "improve validation error message for retired codes" (text change) in [release 6.9.12 notes](https://github.com/hapifhir/org.hl7.fhir.core/releases/tag/6.9.12); version-dependent `code`/`details.text`/`expression` payloads in [issue #2272](https://github.com/hapifhir/org.hl7.fhir.core/issues/2272).
**Confidence:** Text-instability **Verified**; full stability matrix **Reported → EXP-C3**.

#### C4 — FSH→SUSHI→package authoring; alternatives; offline
**Answer:** **FSH + SUSHI** compiles FHIR Shorthand to profile/IG output for **R4/R4B/R5**; **requires Node.js 18 (not JVM)**; Apache-2.0. It does only **basic** validation (paths, cardinalities) — not FHIRPath, terminology, or slice-membership — so profiles still need the official validator. Offline after setup is plausible but `update-dependencies`/IG Publisher fetch packages, so **one-time online setup is required**. Alternatives: Trifolia-on-FHIR (JS/Angular + Java IG Publisher); Firely Forge (proprietary).
**Evidence:** Node.js 18, Apache-2.0, R4/R4B/R5, "basic validation … does not validate … terminological compliance, or slice membership," `update-dependencies` in [SUSHI README](https://github.com/FHIR/sushi); Trifolia-on-FHIR stack in [Lantana free tools](https://www.lantanagroup.com/resources/free-tools/).
**Confidence:** Node dependency + capabilities **Verified**; full offline-after-setup **Inferred**.

#### C5 ⚠ — `-tx n/a` behavior (performed/emitted/skipped) + terminology licenses (primary sources)
**Answer, validator behavior under `-tx n/a`** (precise trichotomy):
- **Performed:** structural conformance, cardinality, datatype, fixed/pattern values, profile-shape, and any invariant/FHIRPath checks not requiring terminology.

#### E7 — Determinism hazards
**Answer:** Validator concurrency race (#2470, non-deterministic exceptions, open); terminology-cache poisoning (#2524, open); locale-sensitive behavior (#2462, open — pin `-Duser.language`); Synthea wall-clock default seeds and default thread pool = CPU count; HAPI HL7v2 canonicalizing encode; NIST engine `Future`-based concurrency (order of async detections).
**Evidence:** [#2470](https://github.com/hapifhir/org.hl7.fhir.core/issues/2470), [#2524](https://github.com/hapifhir/org.hl7.fhir.core/issues/2524), [#2462](https://github.com/hapifhir/org.hl7.fhir.core/issues/2462); Synthea defaults in [Generator.java](https://raw.githubusercontent.com/synthetichealth/synthea/master/src/main/java/org/mitre/synthea/engine/Generator.java); HAPI encode in [PipeParser.java](https://raw.githubusercontent.com/hapifhir/hapi-hl7v2/master/hapi-base/src/main/java/ca/uhn/hl7v2/parser/PipeParser.java).
**Confidence:** **Verified.**

#### E8 — Failure behavior offline / malformed / version mismatch
**Answer:** Official validator degrades to **failures** (not skips) offline for terminology-bound checks (#2272) and can report indeterminate warnings for unknown code systems (C5); HAPI table checks **silently skip** without a CodeStore (D2/D8); CDC wrapper needs cached NIST jars or the build fails; version mismatch between validator and IG packages surfaces as canonical/clash errors (see the package-URL exact-match fix referenced in the validator issue tracker). Malformed-input behavior per engine (HAPI throws `HL7Exception`; validator emits OperationOutcome errors) is deterministic given pinned versions.
**Evidence:** offline failures in [#2272](https://github.com/hapifhir/org.hl7.fhir.core/issues/2272); HAPI skip logs in [DefaultValidator.java](https://raw.githubusercontent.com/hapifhir/hapi-hl7v2/master/hapi-base/src/main/java/ca/uhn/hl7v2/conf/check/DefaultValidator.java); NIST Nexus dependency in [CDC lib README](https://github.com/CDCgov/lib-hl7v2-nist-validator).
**Confidence:** **Verified** (offline/skip behavior); malformed-input specifics **Inferred**.

#### F1 — Prior-art toolkits (deepened; language/license/deploy/embeddability/failure)

**Confidence:** **Verified** (per-tool language/license/deploy/failure); GVT/TCAMT license **Unknown**.

#### F2 — Composition pipelines and every conversion/artifact seam
**Answer:** Natural composition: **Synthea (FHIR) → [seam 1: FHIR→v2 projection via HAPI in a PatientExporter plugin] → HL7v2 → [seam 2: labelled mutation] → gates** (FHIR: `validator_cli` with pinned IG packages + local terminology; v2: HAPI `DefaultValidator` and/or NIST/CDC with IGAMT XML; C-CDA later: Saxon Schematron). **Artifact seams to pin:** (a) Synthea seed+version+config; (b) FHIR IG NPM packages `id#version` + local terminology; (c) HAPI/IGAMT profile artifacts; (d) NIST engine jars (Nexus-sourced); (e) validator binary version. **Confidence:** **Inferred** (composition from verified component seams).

**Answer:** **Not foreclosed.** C-CDA validation is **XSD (CDA_SDTC) + Schematron**; official C-CDA Schematron is HL7-published and executes **on the JVM via Saxon** (as Gazelle's validator does). **Evidence:** schema+Schematron model in [C-CDA companion guide](https://build.fhir.org/ig/HL7/CDA-ccda-2.1-sd/understanding_c-cda_and_the_c-cda_companion_guide.html); Saxon 9HE in [Gazelle Schematron Validator](https://interoperable-europe.ec.europa.eu/collection/interoperability-test-bed-repository/solution/gazelle-schematron-validator); [jddamore/ccda.io MIT/Node](https://github.com/jddamore/ccda.io); [Lantana free tools](https://www.lantanagroup.com/resources/free-tools/).
**Confidence:** **Verified** (mechanism + JVM path); tool choice **Inferred**.

#### F4 — Reproducibility-manifest prior art
**Answer:** **No cross-tool (generation+mutation+validator) reproducibility-manifest standard exists.** Reusable building blocks: FHIR **`package.json` pinned dependencies** (`id#version`, no wildcards) + optional `.index.json`; **npm-style lockfiles** (`package-lock.json`, `npm ci --frozen-lockfile`) — the closest reproducible-restore pattern, applicable to SUSHI; container image SHA256 pinning; Synthea's seed+version identity statement. A project-specific manifest {Synthea version+seeds+config hash; IG package set + terminology hashes; profile-artifact versions; validator binary version+flags; package/terminology cache digests} would be novel prior-art-informed work.
**Evidence:** FHIR pinning/`.index.json` in [packages spec](https://hl7.org/fhir/packages.html); lockfile/frozen-install practice in [npm package-lock docs](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/); Synthea identity in [Basic Setup wiki](https://github.com/synthetichealth/synthea/wiki/Basic-Setup-and-Running); package/terminology cache separation in [FilesystemPackageCacheManager.java](https://raw.githubusercontent.com/hapifhir/org.hl7.fhir.core/master/org.hl7.fhir.utilities/src/main/java/org/hl7/fhir/utilities/npm/FilesystemPackageCacheManager.java).
**Confidence:** **Verified absence** of an integrated standard; building blocks **Verified**.

## Proposed Experiments (one per Unknown, incl. performance and HAPI FHIR round-trip)

**EXP-A4 — Synthea byte/order determinism across thread counts.** *Objective:* identical output bytes for fixed pins while varying `generate.thread_pool_size` (1/4/N). *Inputs:* `-s 12345 -cs 12345 -r 20250101 -p 100`, fixed modules, `-Duser.timezone=UTC -Duser.language=en`. *Artifact:* per-file + directory-manifest SHA-256. *Acceptance:* per-patient content hashes identical across thread counts. *Stop:* if any differ, pin threads=1. *Effort:* Low.

**EXP-B2 — HAPI FHIR + HL7v2 parser round-trip fidelity.** *Objective:* quantify normalization of the HAPI FHIR JSON/XML parser (and confirm HL7v2 canonicalization). *Inputs:* Synthea FHIR bundles; ADT with trailing empty fields. *Artifact:* diff report (input vs parse→encode). *Acceptance:* enumerate all normalization classes (key order, whitespace, trailing delimiters, array handling). *Effort:* Low.

**EXP-C3 — OperationOutcome stability across two pinned validator versions.** *Objective:* measure code/location/text drift. *Inputs:* 6.9.12 vs a prior pinned version; same resources + pinned US Core; `-tx n/a` and with local terminology. *Artifact:* structured diff of `{severity, code, expression, details.text}`. *Acceptance:* classify fields stable vs volatile. *Effort:* Low–medium.

**EXP-C5 — Minimal freely-redistributable offline terminology set.** *Objective:* smallest bundled royalty-free vocab (LOINC/UCUM/ICD-10-CM/HL7-CC0) that validates a target profile offline; document which checks remain indeterminate (SNOMED/CPT). *Inputs:* validator 6.9.12; target IG; incremental CodeSystem/ValueSet packages. *Artifact:* offline run + license inventory. *Acceptance:* zero terminology-caused *errors* for royalty-free-covered bindings; SNOMED/CPT-bound checks documented as license-blocked/indeterminate. *Effort:* Medium.

**EXP-D1 — Trivial IGAMT profile vs HAPI `message_profile.xsd`.** *Objective:* settle IGAMT↔HAPI compatibility. *Inputs:* IGAMT export of a minimal ADT^A01 `PROFILE.xml`; validate against HAPI XSD; attempt `ProfileParser.parse`. *Artifact:* XSD result + parse trace/`RuntimeProfile`. *Acceptance:* parses unmodified → direct compat; else record the transform (XSLT) needed. *Effort:* Medium.

**EXP-D3 — CDC lib fully-offline build/run.** *Objective:* verify one-time acquisition then offline. *Inputs:* CDC lib 1.4.0; pre-fetch NIST 1.6.3 jars into a local mirror; build/run air-gapped with `TEST_PROF`. *Artifact:* successful offline `ProfileManager.validate` → `NistReport`; SBOM + licenses. *Acceptance:* runs with no network; all transitive licenses identified. *Stop:* if NIST engine license cannot be confirmed → adoption blocker. *Effort:* Medium–high.

**EXP-E6 — Resource benchmarks for every candidate.** *Objective:* measure cold-start, steady-state RSS, and throughput. *Inputs:* fixed hardware; Synthea 1k patients; validator single-resource + 10k-bundle; HAPI HL7v2 encode 10k messages; CDC/NIST validate 10k messages; SUSHI compile a fixed IG; IGAMT container boot. *Artifact:* table of startup(ms), peak RSS(MB), throughput(items/s) with 3-run medians. *Acceptance:* stable medians (<10% variance). *Effort:* Medium.

**EXP-SBOM — License/transitive resolution for NIST v2-validation, IGAMT, GVT, and CDC transitives.** *Objective:* resolve the Unknown licenses and transitive compatibility. *Inputs:* full dependency tree (Maven/sbt) + source-header scan + direct inquiry to NIST/CDC if headers are silent. *Artifact:* SBOM with per-artifact SPDX (or "US-Gov work, no explicit license") + a compatibility verdict against Apache-2.0. *Acceptance:* every transitive has a resolved license or a documented risk. *Effort:* Medium.

**EXP-A3/F2 — Minimal FHIR→v2 PatientExporter plugin.** *Objective:* prove the projection seam. *Inputs:* Synthea custom-exporter-template; HAPI HL7v2; emit ADT^A01 `MSH/EVN/PID/PV1` from `Person`. *Artifact:* drop-in JAR; sample messages; HAPI `DefaultValidator` pass. *Acceptance:* deterministic v2 output for a pinned seed; validates against a trivial profile. *Effort:* Medium.

## Top-Risk Register (with mitigations)

1. **Official validator not cleanly offline (terminology).** ([#2272 open](https://github.com/hapifhir/org.hl7.fhir.core/issues/2272)) — *Mitigate:* bundle royalty-free vocab (EXP-C5); gate on structured codes; evaluate a license-cleared local terminology server separately.
2. **Validator concurrency race → non-deterministic errors.** ([#2470 open](https://github.com/hapifhir/org.hl7.fhir.core/issues/2470)) — *Mitigate:* subprocess or single-threaded; pin version.
3. **NIST/IGAMT licenses Unknown; NIST deps off Central (SSL-insecure).** ([NIST repo](https://github.com/usnistgov/v2-validation), [CDC README](https://github.com/CDCgov/lib-hl7v2-nist-validator)) — *Mitigate:* EXP-SBOM; mirror NIST jars internally; fallback HAPI `DefaultValidator`.
4. **HAPI HL7v2 dual MPL/GPL.** ([pom](https://raw.githubusercontent.com/hapifhir/hapi-hl7v2/master/pom.xml)) — *Mitigate:* elect MPL; keep HAPI unmodified in a separate module; MPL file-level copyleft is compatible with an Apache repo.
5. **No HL7v2 generator or labelled mutator exists.** (A2, B1) — *Mitigate:* build the `PatientExporter` projection (EXP-A3) + an in-house labelled mutator with FHIRPath/Terser provenance.
6. **Determinism erosion from environment.** ([#2462 open](https://github.com/hapifhir/org.hl7.fhir.core/issues/2462); [Generator.java](https://raw.githubusercontent.com/synthetichealth/synthea/master/src/main/java/org/mitre/synthea/engine/Generator.java)) — *Mitigate:* pin locale/timezone/seeds/thread-count/versions in the F4 manifest.
7. **IGAMT↔HAPI dialect mismatch.** (D1) — *Mitigate:* route IGAMT profiles to NIST/CDC; EXP-D1.
8. **Message-text drift breaks brittle CI assertions.** (C3) — *Mitigate:* assert on `code`/`expression`; pin versions; EXP-C3.

## Ranking and Tradeoffs (kept separable from findings; no final architecture pick)

- **FHIR generation:** Synthea is effectively unrivaled for seeded longitudinal JVM generation; tradeoff = missing R4B/R5/v2 and filter-based (not direct) characteristic control.
- **v2 generation:** all options require build effort; tradeoff = Synthea-plugin projection (reuses Synthea realism, medium effort, JVM) vs Microsoft FHIR-Converter FHIR→v2 (exists but .NET) vs Mirth channels (Java, heavyweight).
- **FHIR validation:** subprocess official validator (authoritative, isolatable, offline-imperfect) vs in-process HAPI FHIR (same engine, exposes global-state bug). Tradeoff = isolation/determinism vs latency.
- **v2 profile validation:** HAPI `DefaultValidator` (in-process, license clear, no predicates) vs NIST/CDC (full constraints verified in source, license-Unknown + non-Central deps). Tradeoff = constraint completeness vs supply-chain/license cleanliness.
- **Profile authoring:** SUSHI (mature, Node) for FHIR; IGAMT (heavyweight JVM service) for v2. Tradeoff = authoring power vs added non-JVM/service dependencies.

## Methods / Limitations

Repository and artifact state is checked **as of 2026-07-22** using only primary sources fetched during this research: GitHub repositories, raw source files, XSDs, release pages, issue trackers, license files, the GitHub and Maven Central APIs, official HL7/HAPI documentation, and the primary license pages of each terminology. Every external factual sentence carries an inline link to the exact fetched source; no value is taken from memory or from any uploaded document. **Hands-on execution was NOT performed** — nothing was built, run, or benchmarked — so all runtime-dependent claims (Synthea file-order determinism, HAPI FHIR parser byte-fidelity, offline terminology sufficiency, IGAMT↔HAPI parse compatibility, CDC-lib offline build, OperationOutcome cross-version stability, and every startup/memory/throughput figure in E6) are marked **Unknown** with a defined experiment. Where a repository ships no LICENSE artifact (NIST `v2-validation`, IGAMT, NIST GVT), the license is reported **Unknown** rather than assumed, with EXP-SBOM to resolve it. Release labels ("latest") are used only where a fetched release page or releases API established the version and date.
